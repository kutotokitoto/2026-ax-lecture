1-1. 이름의 유래

[ 코디 ]
바이브 코딩이라는 말, 만든 사람이 있어. 안드레이 카파시(Andrej Karpathy) — ChatGPT로 유명한 OpenAI의 창업 멤버 중 한 명이지.
일상 언어(자연어)로 원하는 걸 설명하면, AI가 그걸 실행 가능한 코드로 만들어주는 방식.
왜 '바이브(느낌)'인가 — 사전에 논리를 치밀하게 설계하지 않고, 큰 그림과 직관만 던진다는 뜻에서.
⚠️
오해 방지: "느낌대로"가 "대충"이라는 뜻은 아니다. 오히려 원하는 걸 명확히 말하는 능력이 핵심이 된다.

1-3. 제1법칙

💡 주문의 해상도 = 결과의 해상도
"게임 만들어줘"와 "좌우로 움직이고 스페이스로 발사하는 슈팅 게임 만들어줘"의 차이
AI는 마법사가 아니라 통역사다. 머릿속 그림이 흐리면 나오는 것도 흐리다.

2-3. 설치 4대 천왕

[ 코디 ]
튜토리얼마다 "일단 이거 까세요"라고 하는데, 왜 까는지는 아무도 설명 안 해주지. 오늘 그 부적의 정체를 벗겨보자.
🎭 비유
주방 공사
가스레인지(실행기) + 식자재 배송앱(패키지 매니저) + 레시피 수정 노트(git)
이게 갖춰져야 셰프(AI)가 일을 시작할 수 있다.
팀 1통역사 — 파이썬 / Node.js
CPU는 0과 1만 알아듣는다. 그 사이를 옮겨주는 게 실행기.
"언어와 실행기는 다르다" — 한국어와 한국어 통역사가 다르듯이
Node.js 탄생 비화: 크롬 속 V8 엔진을 뜯어내서 단독 프로그램으로 만든 것. 자바스크립트가 브라우저 밖으로 나온 순간.
"나 자바스크립트 안 쓰는데 왜?" → 클로드 코드 자체가 Node.js 위에서 도는 프로그램이라서
팀 2창고 관리인 — pip / npm
부품을 인터넷 중앙 창고에서 받아다 네 선반에 꽂아주는 심부름꾼
파이썬은 pip, 자바스크립트는 npm
진짜 위대함: 부품의 부품까지 알아서 챙긴다 (의존성 추적)
없던 시절엔 "dependency hell(의존성 지옥)"이라는 정식 용어가 있었다
팀 3타임머신 — git
폴더 상태를 사진 찍어 저장(커밋)하고, 언제든 되돌아가는 도구
최종.zip / 진짜최종.zip / 진짜최종_수정2.zip을 우아하게 대체
바이브 코딩에서 git은 선택이 아니라 생명줄 — AI가 "개선해드렸습니다^^" 하며 멀쩡한 걸 뭉개는 날이 반드시 온다
⚠️ 오개념 교정

"git이랑 GitHub이 같은 거 아니에요?"

다릅니다. git은 내 컴퓨터의 타임머신(무료 오픈소스 도구), GitHub은 그 기록을 올려두는 인터넷 창고(회사 서비스)예요. git은 GitHub 없이도 완벽하게 작동합니다.

8-8. 이름 함정 — REST, OpenAPI

⚠️ 오개념 교정 — REST의 정체

"REST가 GET/POST의 약자인가요?"

아닙니다. REpresentational State Transfer의 약자예요. 2000년 박사논문에서 나온 학술 용어라 어감이 최악입니다.

뜻을 풀면 사실 단순해요 — 자원의 현재 상태(State)를, JSON 같은 형태로 표현해서(Representational), 주소로 주고받는다(Transfer).

실용적으로는 "웹 API를 만드는 국제 표준 매너"로 이해하면 됩니다. 주소로 대상을 가리키고(/users/123), 네 가지 동사로 행동을 표현하죠 — GET(읽기) POST(만들기) PUT(고치기) DELETE(지우기).

⚠️ 오개념 교정 — OpenAPI의 이중생활

"오픈 API랑 OpenAPI가 같은 건가요?"

완전히 다른 두 가지가 같은 이름을 씁니다.

뜻 ①
"오픈 API" — 누구나 갖다 쓰게 공개한 API. (공공데이터포털 등에서 이 의미로 씀) → 개방 상태를 가리키는 말
뜻 ②
"OpenAPI" (붙여쓰기, 고유명사) — API 설명서를 쓰는 표준 양식. 옛 이름 Swagger. 개방 여부와 무관

문맥을 보세요. "공공데이터 오픈 API 써서" = 뜻 ①. "OpenAPI 문서 있어? Swagger 링크 줘" = 뜻 ②.

용어무엇을 말하는가
API창구라는 개념 자체
REST그 창구를 어떤 매너로 차렸나
오픈 API그 창구를 누구에게 열었나
OpenAPI그 창구의 설명서 양식
[ 코디 ]
경쟁하는 게 아니라 각자 다른 질문에 답하는 거야. 그래서 "REST 방식으로 만든 오픈 API인데, OpenAPI 명세로 문서가 잘 돼 있다"는 문장이 완벽하게 성립해.

🎭 비유
풀메이크업과 쌩얼

엑셀 파일(.xlsx)은 사실 압축 파일입니다. 확장자를 .zip으로 바꿔 풀어보면 파일 수십 개가 쏟아져요. 글꼴, 셀 색깔, 테두리, 수식, 시트 구조… 온갖 화장품이 발려 있죠.

CSV는 쌩얼. 데이터라는 알맹이는 똑같은데 포장이 없습니다.

쌩얼의 힘 셋
🌍
아무 프로그램이나 열 수 있다 — 엑셀도, 파이썬도, 40년 전 프로그램도
⚡
다루기가 압도적으로 쉽다 — 한 줄 추가 = 그냥 이어 쓰기
👀
사람이 눈으로 검수할 수 있다 — 메모장으로 열면 다 보임
[ 코디 ]
그래서 프로그램끼리 표 데이터를 주고받을 땐 거의 무조건 CSV야. 은행 거래내역 다운로드, 설문 결과 추출, 측정 장비 출력 — 죄다 CSV인 이유가 이거야. 데이터 세계의 영어.
⚠️ 오개념 교정

"CSV = 엑셀 파일 아니에요?"

지금 당장 해보세요 — 엑셀 파일(.xlsx)을 메모장으로 열면 외계어가 나오는데, CSV는 내용이 그대로 읽힙니다.

이 차이가 중요한 이유는 — CSV는 엑셀 없이도 살아있다는 뜻이거든요.

12-1. 옛날엔 왜 어려웠나

[ 코디 ]
예전에 프로그램 만드는 게 왜 그렇게 어려웠는지 알아? 버튼을 하나씩 그려야 해서가 아니야.
진짜 문제는 — 운영체제마다 완전히 다른 외국어를 썼거든.
윈도우에서 창을 띄우려면 윈도우만의 명령 체계를 배워야 했다
같은 프로그램을 맥에서 돌리려면? 맥은 완전히 다른 체계. 리눅스는 또 다르고
"윈도우용 계산기"와 "맥용 계산기"는 겉보기만 같을 뿐, 속은 처음부터 다시 짜야 하는 별개의 프로그램이었다
🎭 비유
세 나라 언어로 같은 소설을 세 번 쓰기
OS가 셋이면 세 번 만들어야 했다. 이게 프로그램 개발을 소수 전문가의 영역으로 가둔 벽.

12-2. 웹이 괴물이 됐다

[ 코디 ]
그 사이에 무슨 일이 일어났냐면 — 웹이 어마어마하게 커졌어.

HTML/CSS/자바스크립트는 OS를 안 가린다.

윈도우의 크롬이든, 맥의 크롬이든, 리눅스의 크롬이든 — 똑같은 HTML을 똑같이 그려준다.

브라우저가 OS 간 차이를 전부 흡수해주는 만능 중간층이 됐다
"OS마다 세 번" → "한 번 짜면 다 돌아간다"
그래서 지난 20년간 전 세계 개발자가 웹으로 몰려갔고, 웹 기술이 폭발적으로 발전했다
[ 코디 ]
여러분이 1부에서 배운 그 HTML이, 사실 소프트웨어 세계의 중심 대륙이야.

12-3. 일렉트론 — 극장을 통째로 배달하기

[ 코디 ]
근데 딜레마가 하나 남아. 웹앱은 다 좋은데 브라우저 안에서만 살잖아. 주소창 치고 들어가야 하고, 탭으로 열리고.
사람들은 여전히 "진짜 프로그램"을 원한다 — 바탕화면 아이콘, 독립된 창, 작업표시줄
웹의 개발 편의성은 갖고 싶은데, 결과물은 데스크톱 앱이었으면 좋겠다
일렉트론의 발상

"웹앱을, 브라우저를 통째로 껴안은 채로, 독립 프로그램인 척 포장하자."

일렉트론 앱 안에는 크롬 브라우저가 통째로 들어있다. 진짜로.
사용자가 앱을 켜면, 그 안에서 미니 크롬이 웹앱을 띄운다. 주소창도 탭도 없이 앱 화면만 보이니 사용자는 그냥 "프로그램"이라고 느낀다
🎭 비유
극장을 통째로 배달
웹앱은 원래 "브라우저라는 극장에 가야 볼 수 있는 영화"였다.
일렉트론은 그 영화를 극장째로 집에 배달한다.
상자를 열면 안에 극장이 통째로 들어있어서 바로 재생된다.

12-5. 태우리 — 동네 극장 빌려쓰기

[ 코디 ]
근데 일렉트론엔 대가가 있어. 크롬을 통째로 실으니까 앱이 무거워.
세상에서 제일 간단한 앱도 용량이 수백 메가, 메모리도 수백 메가
일렉트론 앱 여러 개 켜면(슬랙+디스코드+VS Code) 컴퓨터가 헉헉댄다 — 극장이 세 개나 배달된 셈
태우리(Tauri)의 발상

"극장을 배달하지 말고, 당신 동네 극장을 쓰세요."

윈도우에도 맥에도 브라우저 엔진이 이미 깔려 있다 (엣지 엔진, 사파리 엔진)
태우리는 크롬을 안 싣고 OS에 이미 있는 엔진을 빌려 쓴다
결과: 용량이 일렉트론의 수십분의 일, 메모리도 훨씬 가볍다
⚠️ 오개념 교정

"그럼 태우리가 무조건 좋은 거 아닌가요?"

아닙니다. 가벼움을 얻는 대신 일관성을 팝니다.

"동네 극장을 빌린다"는 건 극장이 동네마다 다르다는 뜻이거든요. 윈도우의 엣지 엔진과 맥의 사파리 엔진은 서로 다른 엔진이라, 같은 HTML을 미묘하게 다르게 그릴 수 있습니다.

반면 일렉트론은 크롬을 통째로 싣고 다니니까 어디서든 똑같이 작동합니다. 개발자 입장에선 이게 큰 안심이에요.

12-7. 그럼 웹 기반이 못하는 건?

[ 코디 ]

13-1. 폰이 더 심각했다

[ 코디 ]
데스크톱은 그래도 윈도우가 압도적이라 "윈도우만 지원해도 대충 됨"이라는 도피처가 있었어. 근데 폰은?
📱 iOS(아이폰) 와 🤖 안드로이드 가 반반씩 갈라져 팽팽하게 대치.
한쪽만 지원하면 세상의 절반을 통째로 버리는 것.
iOS안드로이드
언어SwiftKotlin
도구XcodeAndroid Studio
제약맥 컴퓨터가 없으면 만들지도 못함윈도우/맥 모두 가능
[ 코디 ]
그러니까 옛날 방식대로면 "아이폰용 카카오톡"과 "안드로이드용 카카오톡"은 완전히 다른 두 팀이, 다른 언어로, 처음부터 따로 만드는 별개 프로젝트였어. 인력 두 배, 비용 두 배, 버그도 두 곳에서 따로.

13-2. 크로스 플랫폼 — 한 번 만들어 양쪽에서

[ 코디 ]
당연히 "한 번 만들어 양쪽에서 돌리자"는 운동이 일어났지. 이걸 크로스 플랫폼이라고 해. 접근법이 두 갈래야.
갈래 1웹을 폰 안에 넣기 (일렉트론의 폰 버전)
폰 안에도 브라우저가 들어있다 (아이폰=사파리, 안드로이드=크롬)
그 브라우저 화면을 앱처럼 껍데기 씌워서 웹앱을 폰앱인 척 만든다
대표: Capacitor (예전엔 Cordova)
원리가 일렉트론과 판박이 — 웹 기술로 만들고, 폰의 브라우저로 감싸고, 앱스토어에 올린다
장점: 이미 웹을 아는 사람이 바로 만들 수 있다
단점: 진짜 native보다 느리고, 폰 특유의 매끄러운 느낌(스크롤이 손가락에 착 붙는 감각)이 살짝 떨어진다
갈래 2하나로 짜서 진짜 native로 변신
웹을 감싸는 게 아니라, 하나의 코드로 짜되 진짜 iOS native와 진짜 안드로이드 native로 각각 변신시킨다
성능도 좋고 느낌도 매끄럽다
⚛️ React Native — 메타(페이스북)가 만듦
웹 만들 때 쓰는 리액트 기술을 폰으로 가져온 것. 웹 개발자가 접근하기 좋다.
각 폰의 진짜 native 부품을 빌려다 쓰므로 "그 폰다운 느낌"이 난다.
🐦 Flutter — 구글이 만듦
자체 언어(Dart)를 쓰고, 화면을 아예 자기가 직접 다 그린다.
그래서 iOS든 안드로이드든 완전히 똑같은 화면이 나온다.
🎭 비유
또 그 대비다 — 빌려 쓰느냐 vs 직접 갖고 다니느냐
⚛️
React Native = OS의 부품을 빌림 (태우리와 같은 철학)
🐦
Flutter = 자기가 다 그림 (일렉트론과 같은 철학)
소프트웨어 세계의 근본 딜레마가 여기서도 반복됩니다.

13-3. ⚠️ 이름 함정 — 리액트 ≠ 리액트 네이티브

⚠️ 오개념 교정

"리액트랑 리액트 네이티브가 같은 건가요?"

다른 물건입니다. 작명이 죄악 수준이라 헷갈리는 게 정상이에요.

웹
리액트(React) — 웹을 만드는 도구. 브라우저에서 도는 화면
폰
리액트 네이티브(React Native) — 폰 앱을 만드는 도구. 앱스토어에 올라감

둘 다 메타가 만들었고 사고방식도 같은 뿌리지만, 결과물이 완전히 다릅니다.

⚠️ 그럼 리액트를 배우면 리액트 네이티브도 되나?

절반은. 사고방식(화면을 부품 단위로 조립, 데이터가 흐르는 방식)은 그대로 이전됩니다. 그런데 화면을 그리는 부품이 다릅니다. 웹에선 <div>, <button> 같은 HTML 부품을 쓰는데, 리액트 네이티브에선 폰용 부품을 써요.

🎭 레고 조립법은 똑같은데 블록 모양이 다르다. 요령은 그대로, 블록은 새로 익힌다.

15-2. Cowork — 터미널 없는 에이전트

[ 코디 ]
코딩 에이전트의 문제가 하나 있어. 터미널에 산다는 것. 그 까만 창이 일반 사용자한텐 무섭잖아.
Cowork의 발상

"강력한 실행 능력은 그대로 두고, 터미널이라는 무서운 껍데기만 벗기자."

🎭 비유
수동 기어와 자동 변속기
코딩 에이전트 = 수동 기어 스포츠카. 강력한데 클러치를 밟을 줄 알아야 한다.
Cowork = 같은 엔진에 자동 변속기. 똑같이 강력한데 아무나 몰 수 있다.
채팅과 뭐가 다른가
일반 채팅은 대화하는 곳 — 주고받는 공간
Cowork는 일을 시켜두고 자리를 뜰 수 있는 곳
예: "이 폴더의 계약서 PDF 30개를 읽고 금액과 만료일을 뽑아 엑셀로 정리해줘" → 혼자 처리하는 동안 커피 마시러 가도 된다
이렇게 여러 단계를 스스로 계획하고 밟아나가는 것을 에이전트라고 부른다

15-3. MCP — 내 도구를 AI가 쓰게 하기

[ 코디 ]
이건 좀 더 깊은 얘긴데, 알아두면 시야가 넓어져.
먼저, LLM은 원래 아무것도 못 한다
AI 모델의 본체는 "텍스트 받고 텍스트 뱉는 기계". 손이 없다
그럼 어떻게 파일을 만지나? → 도구 호출이라는 약속 덕분
모델에게 "이런 도구가 있어. 쓰고 싶으면 정해진 형식으로 텍스트로 선언해"라고 알려준다
모델이 그 형식의 텍스트를 뱉으면, 모델 바깥의 프로그램이 읽어서 진짜로 실행하고, 결과를 다시 텍스트로 돌려준다
🎭 비유
주문서를 받아 심부름하는 집사
AI는 여전히 텍스트만 주고받는다. 옆의 집사가 주문서를 받아 실물 심부름을 한다.
그럼 MCP는?
옛날엔 이 연결이 죄다 수제였다 — 도구 M개 × AI 앱 N개 = M×N번 배선 공사
MCP(Model Context Protocol) = "주문서 양식과 접수창구 규격을 통일하자"는 약속
흔한 비유가 USB-C — 도구 쪽에 규격 포트만 달면 아무 AI나 꽂아 쓸 수 있다. M×N이 M+N으로
⚠️ 오개념 교정

"MCP 서버라니, 서버를 하나 사야 하나요?"

아닙니다. 여기서 "서버"는 인터넷 서버실의 그 서버가 아닙니다. 내 PC에서 도는 작은 프로그램도 서버라고 불러요. "요청 받으면 응답하는 쪽"이면 다 서버거든요.

실제로 사내 도구를 MCP로 만드는 건 대부분 로컬에서 도는 작은 프로그램입니다.

💡 꿀팁 — MCP가 빛나는 순간과 아닌 순간
MCP가 맞을 때: LLM의 판단이 중간에 필요한 일
예: "데이터 받아서(도구) → 이상치가 있는지 보고(AI 판단) → 담당자별로 요약해줘(AI 작문)"
MCP가 과할 때: 정해진 순서대로만 도는 일
예: "매일 밤 백업" → 그냥 파이썬 스크립트 + 스케줄러가 낫습니다

판별 질문: "이 도구, AI가 상황 판단하면서 골라 쓸 일이 있나? 아니면 그냥 자동 재생인가?"
